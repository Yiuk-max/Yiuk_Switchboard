# 联机诊断与待办清单

检查日期：2026-10-16  
检查范围：客户端模组 `mod/`、Go 中转服务端 `internal/` 与 `cmd/relay/`、资源和现有规划文档。  
当前判断：基础链路已具备“房间创建、列表、模组差异查询、sid 配对和 TCP 转发”的实现，但尚不能据此认定多人场景稳定。本文是代码静态检查结果；未进行真实多客户端、断网或压力运行。

## 优先处理

### P0：修复后才能可靠使用

- [x] **房主控制连接断开后自动恢复房间。** 客户端以 5 秒心跳和 pong 超时检测失联，在服务端默认 30 秒保留期内以有界指数退避重新认证并发送 `resume`，恢复后继续监听新会话；重试窗口为 20 秒，单次握手有短超时。服务端允许有效房间 token 接管半开旧控制连接，旧连接后续断开不会覆盖新 owner。恢复失败时停止房间、本地转发并在状态屏提示。控制 JSON 行读取在 socket 超时后保留未完成内容，避免分段到达的行被丢弃。
- [x] **关闭房间时确认服务端结果并清理 UI 状态。** 状态页发送 `close` 后最多等待 4 秒并处理 `ok/err`；成功与未确认结果分开显示。世界退出路径保留快速、幂等的本地清理和尽力发送关闭请求。
- [x] **处理控制连接、重连和转发的关闭竞态。** 增加关闭/重连状态门、控制连接同步替换、关闭时收回活动转发 Socket；旧 reader 不能接管新连接，新 session 不会在关闭后启动。服务端恢复允许 token 接管半开连接；断线保留期计时器按 owner key 校验并原子过期，旧 timer 不会误关已恢复的房间。
- [x] **补足联机故障可观察性。** Minecraft 日志记录心跳、控制连接、恢复、sid 配对准备、转发阶段和关闭失败；房主状态页显示断线恢复、恢复失败和转发错误状态。日志不输出密码、token、sid 或游戏流量。

### P1：核心体验和上线前稳定性

- [x] **调整两个入口按钮的位置和布局。** 两个入口移到页面底部留白区，并根据现有按钮占位选择不重叠位置；小窗口缩窄按钮并尝试备用位置。
- [x] **重命名并区分入口。** 加入入口改为“加入中转房间”，房主入口改为“分享当前世界”，中英文界面文案同步更新。
- [x] **开房/关房在游戏聊天中给出结果提示。** 开房成功后绿色显示房间名和可复制加入地址；服务端确认关闭后发送绿色提示，未确认时发红/黄色提示。都在 Minecraft 主线程执行。
- [x] **向客户端展示完整房间模组清单。** 加入前分页显示房间模组 ID、房间版本和本地安装/版本状态，也列出本地额外模组；空清单保持可读。
- [x] **明确缺少模组和下载/安装路径。** 缺少、版本不一致、本地额外模组分开标注，并明确当前不自动下载，建议按 ID/版本手动安装后重启。
- [x] **增加模组图标资源。** 新增 `assets/yiukswitchboard/icon.png` 并在 NeoForge 元数据中声明 `logoFile`。PCL 中实际显示仍需实机确认。
- [x] **避免房主创建过程的误报与残留。** 先创建中转房间，再开放 LAN 并启动会话监听；认证或建房失败时 LAN 尚未开放，LAN 开启失败则尽力关闭刚创建的中转房间。已有 LAN 端口不会被重复开放或误关。
- [x] **为转发连接设置连接/空闲策略和资源上限。** 客户端限并发 8 个 sid 并去重；服务端增加全局连接上限 `max_connections`，游戏流空闲 300 秒自动清理，可在 30–3600 秒范围配置。待配对和人数仍由原有每房间限制约束。
- [x] **改善错误消息和状态反馈。** 登录/列表/开房/关房将常见服务端错误、地址解析、拒绝连接和超时映射为可操作提示；请求期间禁用重复按钮。刷新失败保留上次成功列表并显示上次刷新时间。
- [x] **处理房间模组查询与列表的竞态。** 请求中禁用列表操作，切屏后丢弃旧结果；校验响应类型和关键字段，遇到旧房间 ID 或畸形清单显示错误而不崩溃。

### P2：运维、安全与发布质量

- [ ] **为控制协议增加 TLS。** 当前连接密码明文传输，README 也已标注只适合可信网络。部署公网前应提供 TLS 或受信任隧道，并验证证书；不得把明文密码方案描述成安全公网配置。
- [ ] **补齐结构化日志上下文和轮转策略。** Go 服务使用 `slog` JSON 文件日志，但日志文件没有轮转/大小上限，主要记录连接、创建、配对和关闭事件；增加错误原因、远端地址（按隐私策略处理）、耗时、活跃会话/拒绝计数等运维信息及轮转说明。严禁输出密码、token、sid 全值和游戏流量。
- [ ] **审视管理端口暴露和拒绝服务边界。** 控制监听绑定 `0.0.0.0`；确认云安全组/防火墙只开放必要端口范围，认证限速表容量行为、未认证连接数、房间创建竞争与慢速 JSON 行均有资源上限。
- [ ] **补上可重复的自动化验证和发布验收。** 现有项目文档称自动化测试尚未建立。建立协议/配置/房间生命周期单元测试和本地集成场景；发布前跑竞态检查与多客户端实测。最低场景：3 名玩家并发、错误密码/坏消息、超过人数上限、房主短断网后 30 秒内恢复、恢复超时、关闭/世界退出、服务进程退出、端口被占用、房主 LAN 连接失败、客户端中途断开。
- [ ] **部署和数据恢复行为文档化。** 服务端房间状态仅驻留内存，进程重启后房间不会恢复；提供服务守护/重启策略、备份配置、日志位置与权限、端口放行、故障排查步骤。确认 README 的编译/运行命令与实际部署目录一致。

## 已确认具备的能力

- Go 服务端具有控制连接认证、按 IP 登录限速、JSONL 行大小限制、房间端口池、人数/待配对限制、随机 sid、待配对超时、房间模组快照、房间关闭和进程退出清理。
- 服务端实现房主断线后的 30 秒房间保留以及基于 token 的 `resume` 协议；**客户端没有接入恢复协议**，所以目前不能算用户可用的断线重连。
- 客户端和服务端对游戏流使用 TCP 双向透明转发；客户端网络工作通过虚拟线程/异步任务执行，界面结果回到 Minecraft 主线程。
- 客户端支持世界退出时调用房间关闭；UI 关房会等待服务端确认，并在聊天区提示结果。
- Go 服务端已有 `slog` 日志；P1 增加了服务端连接上限和游戏流空闲清理，日志轮转仍待 P2 处理。
- 客户端可查看房间完整模组清单和本地差异，但不会自动下载模组；玩家需按 ID/版本自行安装。

## 建议实施顺序

1. 先完成 P0 生命周期和故障可见性，建立不会静默失效的控制/转发行为。
2. 再完成 P1 房主提示、模组详情与差异说明、按钮布局/命名及图标。
3. 进行自动化与多客户端故障注入验证，再决定公网开放前的 TLS 和运维加固范围。
