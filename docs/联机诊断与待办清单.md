### Java + Go 转发卡顿代码审查（2026-10-16）

审查范围：Java 房主端 `HostRoom`，Go 中继 `internal/room/manager.go`、`internal/control/handler.go`、`internal/session/pipe.go` 和协议写入。当前证据解释了一个合理的延迟来源，但没有运行时抓包、计时或原生/中转 A/B 数据，不能把它当成已确认根因。

#### 有代码证据支持的发现

- **修改前 Java 数据 Socket 使用 Nagle 默认行为。** `HostRoom.forward` 原先没有调用 `setTcpNoDelay(true)`；本次尝试已在 `relay` 和 `local` 建连后显式启用 `TCP_NODELAY`。这能避免 Nagle 对小包的等待，但实际体感是否改善仍需要 A/B 测量。
- **数据转发没有定时攒包或额外缓冲流。** `copyBoth` 用两条独立任务分别执行 `relay -> local` 和 `local -> relay` 的 `InputStream.transferTo(OutputStream)`。数据 Socket 使用原始流，没有 `BufferedInputStream`/`BufferedOutputStream`。显式 `flush()` 只用于刚连接 relay 后发送一行 `data + sid` 握手；游戏数据路径没有按时间聚合后再 flush 的代码。握手 flush 对持续移动延迟无关。
- **SO_TIMEOUT 不会在此处造成周期性卡顿。** `relay.setSoTimeout(0)` 明确关闭 relay 数据 Socket 的读超时，`local` Socket 默认也是 0（无限等待）。连接建立阶段的 8 秒/5 秒 connect timeout 只影响新会话开始，不影响已建立后的每个数据包。控制连接使用的 1 秒心跳读取超时属于另一条控制通道，不是游戏数据流。
- **Java 双向流不是串行复制，也没有每块数据共用的 Java 锁。** 两个方向各自在自己的虚拟线程任务中阻塞读写；`Future.get()` 先等待一个方向结束，随后关闭两端 Socket 来唤醒另一个方向。这里没有把两个方向串成一个读写循环，也没有对每个 payload 进行同步锁保护。
- **Go 中继两方向也分别运行。** `session.Pipe` 启动两个 goroutine，各自执行一次 `io.Copy`；任一方向结束后关闭两条连接，再等待另一方向退出。中继数据面不对每个数据块做 Protobuf 编码或写日志。日志在会话配对、会话结束等生命周期节点写入，不在每次 `Read`/`Write` 上输出。
- **Go 写入锁不在游戏数据路径。** `internal/control/handler.go` 的 `client.send` 用 mutex 串行化控制 Protobuf 消息（心跳、`new_session` 等），游戏数据转发由 `session.Pipe` 直接复制，不经过这个锁。竞争只可能出现在会话建立等控制事件上，不应造成持续走路卡顿。
- **Go `io.Copy` 有必要的中继复制，但看不到额外的数据块复制链。** 每个方向都必须把输入从一条 TCP 连接写入另一条连接，数据至少经过 Go 进程并写到另一 TCP socket。房主连接的 `readerConn`/`bufio.Reader` 用于保留读取 `data` 握手时可能预读的游戏字节，避免丢包；这是正确性需要。包装 reader 可能影响 `io.Copy` 某些类型快速路径，但是否产生可测损耗需剖析，不构成已经确认的卡顿根因。
- **中转链路相对原生 LAN 确实增加了用户态读写和复制。** 玩家数据先到 Go relay 的玩家 Socket，被 Go 读入后写进房主 Socket；再由房主 Java 客户端从 `relay` Socket 读入、写到 `local` Socket，最后才到集成服务器。反向数据也经过相反路径。每个代理进程都需要从一条 TCP 流读取并写到另一条 TCP 流；原生 LAN 则是客户端直接与集成服务器建立 TCP 连接，没有 Go/Java 两次应用层转发。因此“经过代理多了一次/多次复制和调度”是架构事实，可能增加 CPU、内存带宽、调度和排队延迟，但当前代码没有证据说明它已成为性能瓶颈。
- **写阻塞会形成 TCP 背压，没有发现无界应用队列。** 两边均是同步的读后写；接收端变慢时复制任务会阻塞在写入，TCP 接收窗口随之施加背压。没有在 Go/Java 之间不断追加 payload 的无界队列。阻塞写确实会延长该方向停顿，但这是透明 TCP 转发的正常流控行为，需区分对端处理慢和网络拥塞。
- **关闭路径有明确的连接收尾。** Java 房间关闭会关闭登记的所有 forwarding sockets，再停止任务执行器；Go `Pipe` 在一方向结束后关闭两端并等待另一 goroutine 结束。正常 socket close 会解除阻塞读写。代码未显示必然残留的转发线程/协程；半开网络、进程被强杀和连接上限耗尽仍应运行时验证。

#### 性能风险（尚未证明为缺陷）

- **Java 转发 Socket 已启用 `TCP_NODELAY`。** 目前没有隔离该改动的对照样本；不同房主表现不一致，不能据此认定它解决或导致了卡顿。
- **中继复制成本尚无量化结论。** 当前代码审查没有发现无界应用队列；必要的 TCP 转发复制不能在保持中继架构时直接省去。暂不安排 profile、抓包或新增运行时统计；若后续有新的可复现样本，再按样本表现决定是否需要代码层面的定向检查。
- **Java 单向复制任务等待一方结束后才统一关闭双端。** 对正常 Minecraft TCP 会话没有问题；如果一端只发送 FIN、仍保持另一方向开放（TCP 半关闭），Java 可能一直等待，另一方向资源继续占用。Go `Pipe` 则任一 `io.Copy` 返回就关闭两端。该差异是关闭/资源生命周期风险，不足以解释正常移动期间每个包的延迟。
- **房主端并发有 8 个会话上限，服务端全局最多 1024 条连接（由配置决定）。** 每个玩家会占用若干虚拟线程/goroutine 和 TCP socket。达到上限时会拒绝或延迟新会话，但不会自然造成已建立会话逐包卡顿；高负载时仍需看 CPU、GC、调度和 socket 队列。
- **每个 Go 会话 reader 有空闲超时包装。** `idleReader.Read` 每次读前刷新读 deadline，300 秒默认超时用于清理空闲连接，不等待固定间隔后才转发；对持续数据不会产生 300 秒批量发送行为。

#### 后续验证方式

以之后自然出现的联机样本作对照，记录房主是谁、原版或整合包、能否进入、区块和操作是否正常、是否断开及大致耗时。无需为此新增游戏流日志、周期统计、profile 或抓包；没有新样本时不据此推断具体根因。

当前结论：**中转架构包含 Go 与 Java 用户态转发；代码审查没有发现定时攒包、无界应用队列或数据面锁。** 这不能确认或排除特定主机、网络、CPU 状态、游戏 tick、模组兼容性等因素。TCP_NODELAY 已有代码尝试，但当前不同房主的结果不一致，尚不能据此定因。

### P3：未来扩展方向

- [ ] **让不同 Minecraft 版本的房间共用同一中转服务。** Go 中转数据面只转发原始 TCP 字节，原则上不需要为每个 Minecraft 版本运行独立服务器进程。客户端模组需要按 Minecraft 版本与加载器分别构建、测试和发布 JAR；每个 JAR 上报自身的游戏版本/加载器，房间列表展示并按兼容条件筛选。控制协议版本与游戏版本分开管理，升级控制协议时保持兼容策略明确。
- [ ] **建立多版本客户端适配矩阵。** 先选定目标 Minecraft 版本和加载器组合，抽离各版本对 LAN 开放、端口读取、原版连接 UI 等内部 API 的适配层；对每个组合维护独立构建配置与实机验收。相同游戏协议的客户端可通过中转互联；不同 Minecraft 协议版本之间默认不兼容，不能仅靠更换客户端 JAR 实现跨版本游戏。
- [ ] **评估跨版本协议转换（可选、独立项目方向）。** 若目标是让不同 Minecraft 协议版本的玩家进入同一房间，需要增加理解并转换游戏协议的代理层，并针对登录、资源包、实体/方块、玩法差异持续维护；这超出当前透明 TCP 中转的职责。先明确目标版本组合、转换范围和兼容性边界，再评估是否采用现有代理方案或自行实现。

## 已确认具备的能力

- Go 服务端具有控制连接认证、按 IP 登录限速、Protobuf 消息长度限制、房间端口池、人数/待配对限制、随机 sid、待配对超时、房间模组快照、房间关闭和进程退出清理。
- 服务端与客户端均已实现房主断线后的短时房间保留与基于 token 的 `resume` 恢复。
- 客户端和服务端对游戏流使用 TCP 双向透明转发；客户端网络工作通过虚拟线程/异步任务执行，界面结果回到 Minecraft 主线程。
- 客户端支持世界退出时调用房间关闭；UI 关房会等待服务端确认，并在聊天区提示结果。
- Go 服务端已有 `slog` 控制面生命周期日志；不将其扩展为游戏流逐包或周期性观测。P1 增加了服务端连接上限和游戏流空闲清理。
- 客户端可查看房间完整模组清单和本地差异，但不会自动下载模组；玩家需按 ID/版本自行安装。

### 2026-10-17 用户反馈复查：设置图标、密码表单、模组差异与严重卡顿

- **设置入口位置：** `SavedRelayServerEntry` 是原版多人游戏列表的自定义服务器行，行尾有齿轮点击区域并打开该条目的编辑表单。此前绘制的齿轮用少量方块拼成，视觉上不够像齿轮；本次加粗齿齿轮并继续使用原版按钮底板/悬停底板。仍需在目标分辨率实际看图确认尺寸与点击区。
- **表单文字/密码：** “记住密码”按钮初始状态应随表单状态显示；文案改为“是/否”，保存动作统一明确写“保存”。密码输入已恢复明文显示。存储仍是本地配置明文，这一点在新增/编辑页提示。
- **模组清单：** 只按房间要求清单逐行展示，避免把本地额外模组误当成房间要求；名称/房间版本在左，状态在右。状态仅显示“一致”(绿)、“缺失”(红)、“不一致”(黄)。`INVALID` 畸形条目按黄色不一致兜底，正常服务端快照校验应阻止此类数据。
- **代码证据（数据通道）：** `HostRoom.forward` 对中继与本机 LAN 两个游戏 TCP Socket 开启 `TCP_NODELAY`、KeepAlive；`copyBoth` 两个方向由独立任务执行，读到数据后直接写出，无应用层定时聚合或逐包日志。Go `session.Pipe` 同样启动两个独立 goroutine 调 `io.Copy`，一个方向结束后关闭两端并等待另一个退出；没有每包锁或日志。控制通道上的 Protobuf 帧写入 不参与游戏数据面。
- **代码证据（额外开销/风险）：** 每个游戏字节确实需要经玩家到 Go、Go 到房主 Java 转发 Socket、Java 到集成服 LAN listener 的用户态读写路径；实现存在至少一次额外的用户态复制和调度，不能仅凭“复制”断言达到不可接受延迟。Go `idleReader.Read` 每次读前更新 socket read deadline，增加 syscall/锁开销的可能性，但当前没有 profile 证据表明它造成明显延迟。`io.Copy`/`InputStream.transferTo` 在下游慢时同步阻塞写，属于 TCP 背压的预期传播；如果下游停顿会让相应方向阻塞，需实测确认是否持续积压。
- **尚未证明的运行时假设：** 房主本机视角也卡可能来自房主发送包经公网绕行到中继再回来、TCP 重传/拥塞/排队、服务器/玩家 Mod 改变 tick 或移动同步、游戏线程过载或渲染掉帧。主机本机的局域网直连流畅只能说明 LAN 路径正常，不能排除游戏逻辑差异。此前 `TCP_NODELAY` 改动后曾反馈可接受，但本轮用户报告卡到不可接受；这两次主观反馈都没有抓包、RTT/抖动/丢包、队列时延或原生对照数据，不能认定根因已修复。
- **后续验证按新样本进行：** 用户报告另一位朋友做房主时完全正常，而第一位朋友的房主样本异常。暂以不同房主、原版/整合包和实际连接结果做对照；不添加游戏流日志、周期统计、profile 或抓包要求。样本不足时保留未定结论。
- **稳定性/资源检查结论：** 当前 Go 每方向独立 goroutine，Java 每房间任务使用虚拟线程且转发连接上限为 8；Go 连接会配对后双向复制，任何方向结束会关闭 socket 解除另一方向阻塞。代码有关闭活动连接的路径；但没有真实故障注入/线程与 goroutine 数量曲线，残留任务和慢客户端资源行为仍待压测确认。
